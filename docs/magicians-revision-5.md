# Revision 5 (reply to the thread: the Sepolia run)

The evidence run is on Sepolia. On 2026-10-26, between blocks 11994931 and 11995051, the script deployed both registries and the two reference consumers, published the two example specifications, created the four example bindings (the principal's binding for an assistant with a guardian holding suspend and resume rights, the swarm charter, a member binding derived from it, and a worker's own binding naming the task publisher as an intervener), and ran the three loops of the text against them: 36 transactions, every one successful.

What the chain shows, read back after the run. On the account path, the operator's `borrow` went through; the guardian suspended with "no new risk" and "de-risk only" set and the hash of its response document; the next `borrow` was refused with `BindingNotSatisfied(NotSatisfied, [Suspended])` while `repay` went through under the de-risk-only set; the guardian lifted its own suspension (the principal could not), and `borrow` went through again. On the task path, against the live TASK-KERNEL v3.0 `TaskToken` at `0xA62059A498E40C4Ae4aF926E2B00C1Ff122bDdb7` (task #20), the adapter accepted the bound worker — `Judged(Satisfied, [its binding], [None])` — and the kernel's own `acceptFulfillment` paid the reward, then rejected the unbound submitter with `NoBinding`. In the lifecycle phase the principal's full stop refused even `repay`; after the charter's termination the derived member binding checks `ParentNotSatisfied` with an empty response set while its own record stays `Active`; version 1 of the swarm specification is deprecated with the bindings unaffected.

Addresses: `ASFSpecificationRegistry` `0x1939665F5905d0d9135Da4f27e36f1B8c84E014b`, `ASFBindingRegistry` `0xc3e1A1Cb021Ab96EBBeD3279018840016114A5c4` (library `ASFEvaluation` at `0x663B84f1BfcE37bE4a78358b0301B5d5E5079269`), `ASFGuardedAccount` `0x40AaD5106A7a13B15892E53099f6bD06bCF80aD3`, `ASFTaskTenderAdapter` `0x51772fabFB757Fb5A4186c0435Ec4fa76D75CE4e`. All seven deployed contracts are verified on Sourcify (runtime and creation match). The record — every transaction with hash, block and gas, the decoded events, the state read back with `eth_call`, and the commands to reproduce the checks — is in `docs/sepolia-evidence.md` and `deployments/` of the repository.

One implementation change came out of the run, and I want to state it plainly because it touches the reference implementation in the pull request. Sepolia's current gas schedule prices code deposit about ten times higher than before, and a transaction may use at most 16,777,216 gas; the revision-4 binding registry (13.3 KB of runtime code) needed about 20.9 million gas to deploy and could not be deployed at all. The registry's evaluation — Section 10.1, the combinators, the requirement validation and the response-set rule over a derivation chain — now lives in `ASFEvaluation`, a library linked externally and called with the registry's storage; the project compiles via IR. The registry's code fell to 9,660 bytes and deployed at 15.1 million gas. Nothing normative changed: the interfaces, the identifiers (`0x1ff33bef`, `0x9bddde77`), the `requirementId` encoding, the vectors and all 84 tests are as in revision 4; the first post and the pull request carry revision 5 with the library added to the reference implementation. The first Sepolia attempt, sent with the gas limit of the Anvil rehearsal, ran out of gas; it is recorded as well.

The five questions of the first post stand, and the shared-budget coordinator remains the next closed loop.
